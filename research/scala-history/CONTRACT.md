# Historical Scala library research contract

## Mission

Build evidence-backed development, review, refactoring and hardening skills, complementing rather than replacing existing Scala skills. Research the inclusive UTC window 2018-01-01 through 2024-12-31. This is a historical cutoff, not a claim that all contributions in that window were human-only. Required repositories: zio/zio, zio/zio-kafka, zio/zio-http, typelevel/cats, typelevel/cats-effect, http4s/http4s, typelevel/fs2, playframework/playframework, and an enumerated inventory of Li Haoyi's Scala libraries and tooling (including archived/transferred repositories and exclusions with reasons).

Read primary source at historical SHAs and PR discussion/review history. Separate observed code organization from explicit reviewer guidance, and reviewer identity from verified historical maintainer role. An approval, merge, contributor count, present-day association, or PR description alone is not evidence of a creator's review preference. Include competing patterns and version boundaries: ZIO 1/2, Cats Effect 2/3, Scala 2/3, JVM/JS/Native. Do not homogenize direct-style Li Haoyi APIs and effect-polymorphic Typelevel APIs.

## Durable state and ownership

Use a state directory outside the public clone, supplied by `--state`; default `~/.local/share/dot-agents/scala-history-2018-2024`. Raw GitHub content, process logs, prompts, checkpoints and evaluation artifacts live there. Public, original skill prose and compact attributed evidence references may later be promoted into the catalog. Never read credentials, change runtime approvals, publish to GitHub, commit, push, change other profiles, or execute downloaded Scala/build scripts. Workers must not spawn workers. Only the integrator edits catalog/generated files. Research workers own their single candidate directory; peer reviewers own separate review files. Preserve existing dirty-tree changes.

The supervisor uses independent Hermes processes: normal `AIAgent` Python-library sessions for skill authors and one-shot CLI sessions only for read-only reviewers. Installed Hermes one-shot mode prohibits skill creation; never override that restriction or clear its approval/lifecycle marker. Require a real authored candidate and independent peer acceptance before full fanout, not merely a successful ordinary-file write. The supervisor explicitly pins `openai-codex` / `gpt-6-astra-900k`, caps concurrency, turns, per-job wall time, attempts and total runtime, and checkpoints each completed step. A process exit is not acceptance. No result is accepted without schema/artifact validation. Resume completed jobs only when their evidence and artifact hashes still match. Refuse concurrent supervisors and live orphan writers. Handle cancellation and process groups. Checkpoints survive reboot; active processes do not.

## Collector interface (Python standard library, gh CLI)

Module `scripts/scala_research/collector.py` exports:

- `discover(state: Path) -> dict`: persist/return `inventory.json`, schema below. Enumerate paginated public repositories for `lihaoyi` and `com-lihaoyi`; include the required core repositories, documented aliases and other clearly attributable transferred libraries. Classify exclusions explicitly; preserve unknowns for research rather than silently dropping them.
- `collect_repository(state: Path, repo: str, *, per_year: int = 6) -> dict`: persist/return `<state>/corpus/<owner>--<repo>/index.json`. Cache raw API responses on disk. Sample PRs by historical year with transparent search counts, incomplete-results and pagination/selection limits. Include merged and rejected/closed discussions, not only popular successes; report unavailable years/data. Collect PR detail, all review summaries, inline review comments, issue discussion, changed files and commit metadata. Collect historical source snapshots (2020, 2022, 2024 or nearest available within window) with commit SHAs, tree paths, and representative actual build/source/test content. Return only after atomic index publication. No full-history/exhaustive claim from a sample.
- CLI `python3 -m scripts.scala_research.collector --state PATH discover` or `... collect OWNER/REPO [--per-year N]`.

Inventory: `{schema_version: 1, window: {start, end}, repositories: [{repo, family, included, reason, ...}], ...}`. `repo` is canonical `owner/name`; `included` boolean. `family` one of `zio`, `typelevel`, `http4s`, `play`, `lihaoyi`. Each entry is unique case-insensitively. Inventory includes explicit pagination/coverage data. Discovery failure must fail closed, not replace a complete old inventory with a partial one.

Corpus index: `{schema_version: 1, repository: "owner/name", window: {start,end}, pulls: [{number, path}], activity_pulls: [{number, path, outcome, stratum, contextual_only, activity_eligible, body_sha256}], snapshots: [...], coverage: {...}, gaps: [...], ...}`. The additive activity sample inspects at most six candidates in each of two strata (pre-cutoff-created open PRs and PRs closed after cutoff), with at most two search pages per stratum. It requires retrieved in-window discussion/commit activity, not creation/update/closure metadata alone. Inspect both PR arrays. Honor each artifact's `historical.eligible_ids`, endpoint coverage, `activity_counts`, `diff_eligible`, `contextual_only` and `adopted_in_window` separately. Supplementary records have no synthetic year and their current diffs are never historical implementation evidence; independently pin and date-check source SHAs before implementation claims. `path` for each PR is relative to the directory containing index.json, resolving to JSON with PR details and full retrieved discussion. Dates and immutable commit references must be retained. API/network/rate-limit failures are bounded/retryable and recorded; never silently mark failed endpoint fetches as empty complete lists. All writing must be atomic. Validate repository identifiers and local path containment.

## Candidate/report interface

One research job per included repo. It writes `<state>/candidates/<owner>--<repo>/report.json` plus `skills/<skill-id>/SKILL.md`, `skills/<skill-id>/references/evidence.json`, and optional reference/fixture files. No candidate is installed automatically merely because it was written.

Report required fields:

- `schema_version: 1`, `repository`, `status` (`complete` or `blocked`), `summary` (string), `gaps` (array of strings).
- `evidence`: array of records `{id, kind, repository, url, occurred_at, excerpt, interpretation, ...}`. Kinds: `review-comment`, `issue-comment`, `review`, `code`, `commit`, `documentation`. URLs must be original GitHub sources; code/doc URLs must pin a full commit SHA. Only content in the window supports historical rules. Exact excerpts must be short, attributable and verifiable against cached raw evidence, not fabricated. For code, include `commit_sha` and `path`; for reviewer claims include `author` and `role_basis` (or explicitly `unknown`). Keep source and inference separate.
- `claims`: array `{id, rule, evidence_ids: [...], applicability, counterexample}`. A rule is a testable decision/procedure, not a vague aesthetic preference. Evidence IDs must resolve. Mark inference in the rule or applicability when no explicit reviewer said it.
- `skills`: array `{id, claim_ids: [...], kind}` where kind is `development`, `review`, `refactoring`, `hardening`, or `organization`. Skill directory name equals frontmatter name. Use focused globally unique names beginning `scala-`, not a generic skill per repo.
- `coverage`: object with `examined_prs` (unique positive PR-number array), `years_sampled` (unique integer UTC-year array), `inspected_source_paths` (repository-relative string array), `substantive_reviewer_exchanges` (discussion evidence-ID array), and `gaps` (string array). No invented totals; derive from persisted data.

Each candidate skill requires: precise trigger/non-triggers; prerequisites/version detection; actionable workflow; invariant-preserving refactoring or review procedure; concrete validation steps using the target repo's actual build; false-positive warnings; output contract including file:line, severity, evidence and test; limitations; relative link to evidence; at least three cited evidence records spanning at least two historical PRs/commits, including actual source/test evidence. A review-preference claim additionally requires substantive review/discussion evidence (not approvals). Record at least one good example, one broken example with correction, and one should-not-trigger case. Use original paraphrases and only short attributed quotations; no mass copyrighted source copies in public skills.

`references/evidence.json`: `{schema_version: 1, repository, evidence: [records used by skill], claims: [claims used by skill]}`.

## Independent review and behavioral evaluation

Peer review output `<state>/reviews/<repo-key>.json`: `{schema_version: 1, repository, verdict: "accept"|"revise"|"blocked", report_sha256, findings: [{severity, skill_id, problem, evidence}], verified_evidence_ids: [...], evaluated_skills: [{id, positive, negative, repair, holdout, result, notes}], ...}`. Reviewer must read the actual candidate report/skills, reopen source evidence, validate dates and attribution, challenge inference and duplicated rules, and exercise each skill on concrete positive, negative, repair and held-out historical cases. `positive`, `negative`, `repair`, `holdout` are evidence paths or substantive evaluation explanations, not booleans; `result` is `pass` or `fail`. Record whether evaluation is model-based or actual compilation/execution. Never label a text simulation as compiled Scala or a proven improvement over baseline.

Reject shallow generic advice, fabricated sources, anachronistic APIs, unsupported maintainer attribution, duplicated adjacent skills, unbounded refactors, and skills that cannot guide a concrete review. When historical coverage is thin, produce a blocked/gap report rather than filling quotas. Allow bounded repair rounds with another review. Catalog promotion additionally needs cross-repository deduplication and final repository gates.

## Completion

Target at least 36 distinct accepted skills with meaningful coverage of development, review, refactoring and hardening. This is a depth target, not permission to pad. Every included repository must have a reviewed research outcome or explicit blocker; exclusions are visible. Persist a coverage matrix and sources, quality decisions, evaluation artifacts, limitations and reproducible commands. Final integration updates catalog hashes, review records, catalog docs and installer rendering without losing unrelated edits. Run `make test` and `make check`. Only report accepted/promoted counts measured from artifacts. Running jobs, candidate files and structural lint are not finished useful skills.
