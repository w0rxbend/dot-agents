# Toolchain and bytecode compatibility

Mill's launcher JVM runs build definitions. `mill-jvm-version` selects it; distribution/version strings can select managed JDKs. Individual JVM modules use `jvmVersion`. Compiler flags control emitted bytecode/API constraints. These three choices are related but not interchangeable. Defaults vary by Mill version; inspect the effective values rather than assuming whichever `java` happens to be on PATH is used.

For the runnable mixed example, application modules use `temurin:21.0.8`; Java uses `--release 21`, Scala uses `-release 21`, and Kotlin uses `-jvm-target 21`. Compiler versions are Scala 3.8.2 and Kotlin 2.2.20. The build launcher uses `system`, explicitly requiring an installed compatible JDK; a new CI project can replace that choice with a managed pin. Verify Kotlin's API constraints separately when compiling on a newer JDK for an older target.

For VSS, current official stack guidance uses Java 25 virtual threads and Scala 3. Give that service a deliberate Java 25 toolchain and target according to its deployment policy. Do not raise a shared Java 17/21 API library's runtime minimum unless required. A service can consume older bytecode; the reverse is not possible. Ox/Tapir and other libraries may impose minimum compiler/JDK versions independently of Mill.

Use the JVM index/distribution options documented for the project's Mill version, and pin the index/download when full repeatability requires it. `system` is a valid explicit local choice but creates an external dependency on machine configuration. Unsupported OS/CPU distributions need a tested alternate rather than an unreviewed URL. `./mill java`, `javac`, `javap`, `jps`, and `jstack` expose the build JVM tools on versions supporting these commands; verify that they target the intended JVM before troubleshooting an application process.

Model a runtime compatibility matrix with cross modules when it provides evidence a released library actually needs. Limit combinations to supported axes rather than multiplying all Scala versions, JDKs, platforms, and flags into an expensive Cartesian product. JVM cross-building is not automatically a Scala binary cross-build; define each axis and its artifact/version policy deliberately.

Compiler plugins often impose tighter constraints than ordinary libraries: Scala full-version plugins, Kotlin compiler plugins tied to `kotlinVersion`, matching KSP/Kapt releases, and annotation processors affected by JDK behavior. A generic JavaModule trait can centralize release flags; language traits need separate compiler settings. Verify settings on nested test modules so tests do not silently compile against a newer runtime.

For Spark, select Scala/JDK according to the actual Spark distribution. For Scala.js/Native, align platform-specific compiler/runtime artifacts; a JVM jar cannot satisfy a Native or JS classpath. For GraalVM native-image, pin the distribution and test dynamic/reflection/resource behavior. These platform requirements should live with the relevant module family, not in an indiscriminate repository-wide convention.
