# Camera frames and device wire compatibility

The paired public implementations are [spycam FrameProtocol.h](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/include/FrameProtocol.h), [spycam-s3 FrameProtocol.h](https://github.com/worxbend/spycam-s3/blob/71e0ef4b7c55a2313f596710e53d3f52ddec19cc/lib/frame_protocol/src/FrameProtocol.h), and [instachron device parser](https://github.com/worxbend/instachron/blob/20cbe22e947d5bfec2a86783886935b0bef196d3/services/tcp-camera-backend/internal/protocol/protocol.go). Numeric widths/order are part of the deployed ABI:

| Variant | Prefix before JPEG bytes | Fields |
|---|---|---|
| JPGS legacy | 16 bytes | four-byte magic, uint32 sequence, uint32 JPEG payload length, uint32 device millis |
| JPGD device | 20 bytes | the same 16 bytes with JPGD magic, then uint32 camera ID |

Fields are big-endian; payload length counts JPEG bytes only, excluding the camera-ID extension. Reading a JPGD packet as a 16-byte legacy header leaves camera-ID bytes in the stream and corrupts framing. Decode magic before deciding the remaining prefix length. Device millis is a wraparound uptime counter, not wall-clock Unix time. Both firmware peers emit the same JPGD 16-byte header plus four-byte camera ID; protocol edits need byte fixtures from both peers and the host parser, without copying their different board/camera settings.

The [proxy-to-proxy streamproto](https://github.com/worxbend/instachron/blob/20cbe22e947d5bfec2a86783886935b0bef196d3/shared/streamproto/streamproto.go) is a separate 32-byte MJPG protocol with version/header fields, nanosecond timestamp, camera ID, uint64 sequence and payload length. Do not merge it with firmware ingress just because both carry JPEG. Validate exact-read behavior, maximum/zero length, EOF in each prefix segment, truncated JPEG, plausible SOI/EOI markers and multiple frames in one transport read. JPEG marker checks do not prove full image validity. Keep allocation caps before allocating the advertised length.

TCP reads/writes are not packet boundaries. A sender must handle partial writes and bound elapsed send time; after a partial failed frame, closing the connection prevents the next header from being mistaken for the old payload. The [spycam sender](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/src/TcpFrameSender.cpp) reconnects before it holds a camera buffer and disconnects after send failure. The [spycam-s3 sender](https://github.com/worxbend/spycam-s3/blob/71e0ef4b7c55a2313f596710e53d3f52ddec19cc/src/TcpFrameSender.cpp) preserves the same connection-before-borrow and close-after-partial-failure boundary. Their sender tasks release the borrowed frame regardless of success. Follow that ownership through the latest-frame slot too: replacing a stale frame must return the old driver buffer exactly once. Do not keep a borrowed framebuffer across reconnect sleep or use it after return.

The camera configuration in [CameraManager.cpp](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/src/CameraManager.cpp) selects PSRAM/DRAM and frame-count fallbacks. Check the target board and [Espressif camera driver](https://github.com/espressif/esp32-camera) before increasing resolution or buffer count. More buffering can increase latency or exhaust memory.

LED control uses other ABIs. The [led-matrix-controller parser](https://github.com/worxbend/led-matrix-controller/blob/6061b81763740885d61af745e14cc633aa35c2e6/src/FrameParser.cpp) has a five-byte header, uint8 payload length and XOR checksum; its buffer must accommodate header + 255 + checksum. [neoncore MatrixProtocol](https://github.com/worxbend/neoncore/blob/6eb16847d95ff6cd0847c32c1a3b698f3057ce98/src/MatrixProtocol.cpp) has its own status command/response. Preserve explicit resynchronization/error behavior and shared byte vectors rather than carrying opcodes across projects by name. Test garbage prefix, partial header/body, checksum error, maximum length and recovery into the next valid frame.
