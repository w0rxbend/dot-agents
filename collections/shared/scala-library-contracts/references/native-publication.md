# Native ownership and publication compatibility

## OpenCV ownership

Establish whether API returns owned data, borrows object, transfers handle or consumes high-level image. In scalacv: `Managed.release` detaches once; `take` transfers without freeing; `use`/`scope` clean up on exceptional paths. Register each acquisition immediately: allocating several Mats before entering finally block leaks earlier ones if later allocation fails. Adopted existing handle must not acquire second independent owner. Value leaving scope must be plain data or separately owned, never scoped native object. See [ownership and scoped-acquisition implementation](https://github.com/worxbend/scalacv/blob/4bdd86f7ac8dfcc68f733f3105760a7251df1ba4/core/src/scalacv/Managed.scala).

Atomic release prevents second free; it does not prove concurrent native use and release safe. Keep thread-safety claims separate. Test consumption/reuse errors before JNI, exception cleanup, transfer versus copy, release count. Native-memory regressions need project's native leak/RSS harness; JVM heap assertions cannot see Mat buffers.

Route new native operations through existing [OpenCv.load boundary](https://github.com/worxbend/scalacv/blob/4bdd86f7ac8dfcc68f733f3105760a7251df1ba4/core/src/scalacv/OpenCv.scala). Its bundled dependency resolution deliberately avoids eager loading of whole JavaCPP OpenCV preset and speculative ELF/Mach-O loads; those can add headless GUI dependencies or interpose incompatible system OpenCV ABI. Preserve its platform-specific loading rules and containment checks. Unparseable linker error does not justify bulk loading.

At interop boundaries preserve channel order, depth, dimensions, stride, ownership. Cropped or padded raster is not necessarily one continuous byte array. Reviewed conversion handles non-contiguous Mats separately, validates supported depths/channels, uses widened size arithmetic, releases allocation if filling throws. See [Mat and BufferedImage conversion](https://github.com/worxbend/scalacv/blob/4bdd86f7ac8dfcc68f733f3105760a7251df1ba4/core/src/scalacv/Interop.scala).

## Build JVM, bytecode floor, and Scala floor

These are independent choices. Reviewed scalacv build bootstraps Mill with JDK25 but intentionally publishes Scala3.3.8 LTS and Java17 bytecode. TASTy compatibility is compiler concern; newer build JVM must not silently raise either consumer floor. Build's JDK matrix reads `MILL_JVM_ID` through tracked task input; setting `JAVA_HOME` while every module pins another JDK does not test claimed matrix. Read current build; do not copy these snapshot versions. See [compatibility, toolchain, native classifier, and POM configuration](https://github.com/worxbend/scalacv/blob/4bdd86f7ac8dfcc68f733f3105760a7251df1ba4/build.mill).

Separate portable APIs from platform-specific native binaries. scalacv publishes classifier-less OpenCV API dependencies; host classifiers belong to test/example/runtime setup. Validate Linux and other supported classifiers; reject combinations where upstream publishes no native artifact. Inspect generated POMs; do not assume Mill strips classifiers as intended. Preserve published artifact names and optional effect integration modules.

## Contract checks

For scalacv, reviewed CI separates selectors with `+` where test commands would otherwise consume following arguments: `./mill core.test + zio.test + examples.test`. CI also runs `docs.mdocCheck`, `leaks.test`, POM assertions, Java consumer smoke. Pick subset relevant to change; follow current [consumer/JDK/publication checks](https://github.com/worxbend/scalacv/blob/4bdd86f7ac8dfcc68f733f3105760a7251df1ba4/.github/workflows/ci.yml).

Gitea: preserve Java21 API floor, warnings catching discarded ZIO effects, checked-in `compatibility.check` baseline. Codeberg4s: use its current formatter, Scalafix, coverage and MiMa configuration, not another library's gates. These are maintained contracts, not universal Scala flags. See [Gitea modules and public API gate](https://github.com/worxbend/gitea-scala-client/blob/2590501c22c8dd0bba216c24b2e03e6da873b313/build.mill) and [Codeberg modules and compatibility configuration](https://github.com/worxbend/codeberg4s/blob/94fe214cccd7b077b9151ab456e256931cb69800/build.mill).

JVM-signature API golden records only erased and generic types, not parameter names or default-argument values. Renames and default changes therefore pass both golden and japicmp; verify them from TASTy or source. Distrust `getGenericParameterTypes` for extension methods with own type-parameter clause: Scala 3.3 emits malformed `Signature` attribute (one parameter, undeclared type variables), and `Try(...).getOrElse(erased)` renderer silently truncates line. Compare generic and erased arities; fall back to erased list. Scala 3 bytecode facts that show up as new JVM-public golden lines: `private val` in companion, read from class body, becomes public static mangled accessor (`scalacv$Image$$$Name`; inline it or use class-private `def`); user-defined case-class companion `apply` with default argument emits `apply$default$N`, which synthetic `apply` never had; super-constructor argument containing lambda is hoisted into public `$superArg$N` method; companion-private helper called from class compiles to mangled public accessor.
