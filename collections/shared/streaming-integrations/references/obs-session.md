# OBS WebSocket v5 sessions

The Scala session implementation is evidence for the existing design, not a mandate to rewrite Crystal or Rust clients: [SessionLogic.scala](https://github.com/worxbend/obs-websocket-client/blob/fd2f2d05aa4a258b1851d0ed93bb33158977a9ac/core/src/com/worxbend/obs/websocket/client/SessionLogic.scala) and [SessionWire.scala](https://github.com/worxbend/obs-websocket-client/blob/fd2f2d05aa4a258b1851d0ed93bb33158977a9ac/core/src/com/worxbend/obs/websocket/client/SessionWire.scala). Re-check the repository's negotiated RPC version before adapting an upstream example. The authoritative wire reference is [obs-websocket protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md); its moving branch must be matched to the target OBS release.

Preserve the handshake state machine: Hello (opcode 0), Identify (1), then Identified (2). Requests become legal only after identification and successful version negotiation. Password authentication derives the challenge response according to the protocol; never log its inputs or cache a challenge-derived value across sessions. Receiving a newer offered RPC version does not automatically negotiate that version.

A request ID identifies one pending operation within one connection generation. Reserve its pending entry before enqueuing the send so an immediate reply can be correlated. Roll it back if enqueueing fails. Check both response opcode (7 for a request, 9 for a batch) and the expected request type. Treat negative requestStatus as a server rejection; absent optional responseData on success can be an empty object when the decoder contract permits it. Ignore or record late and duplicate replies without completing a different operation.

Timeout, explicit cancellation, disconnect, and send failure must all release pending entries and complete callers once. A canceled request still queued for sending must be checked at the sender boundary. A stale timeout callback from an old generation must not cancel a new request that reused an ID. Dispatch user callbacks outside a serialized session actor/lock; callback exceptions must not corrupt correlation state.

Bound outgoing commands and incoming events separately. Choose the overflow behavior by semantics: dropping old display telemetry may be acceptable; silently dropping commands or transactional replies is not. Surface dropped-event counts. On reconnect recreate session-scoped subscriptions and refresh any state that might have changed during the gap. Preserve application intent separately from transport queues.

Do not replay a command merely because the connection was interrupted: Toggle*, a scene change, and starting/stopping outputs have observable effects, and a timeout does not prove non-execution. For an authorized retry, inspect or reconcile current state and use a bounded retry policy. Test handshake rejection, fast response, wrong type/opcode, duplicate response, timeout/send races, queue saturation, disconnect completion, and reconnect with a stale timer. The existing Rust [reconnect policy](https://github.com/worxbend/obsctl-rs/blob/d5d732c118a1d5c5a5eb94646f6c8d3f6d0985b4/src/runtime/reconnect_policy.rs) provides a pure-policy example.
