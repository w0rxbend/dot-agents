# Generated source and resource pipelines

The `assets/codegen` template has a Java `app` module, `app/message.txt`, and a tracked `schema` source task. `generatedSources` reads that input, validates the deliberately limited example format, writes `example/Generated.java` under its destination, and returns `super.generatedSources() ++ Seq(PathRef(Task.dest))`. The application prints the generated value. The example uses simple text to demonstrate task behavior; production schema generation should use the actual schema parser and escaping rules, not a string interpolation shortcut.

Run `./mill app.run`, repeat `./mill app.generatedSources`, then change the declared input and rerun. Verify the output changed and the application recompiles appropriately. Inspect output-file timestamps/signatures to demonstrate the no-change cached result without relying on console log wording. A generated source task that executes on every compile despite unchanged input may have hidden nondeterminism or an uncached dependency.

For OpenAPI/protobuf/SQL/schema generators, model four inputs: source schema, generator version/classpath, configuration/options, and any referenced schemas. Put a generated client in a separate library module when multiple consumers share it. Published generated APIs need stable package names and compatibility policy, even if the schema file is small. Keep generated sources separate from hand-written files so local formatting/refactoring commands do not alter them.

For resources such as a frontend bundle, read `client.bundle().path` inside the backend's resource task, copy the required output into `Task.dest / "static"`, and return the resource directory along with existing resources. The call creates an edge from frontend to backend packaging. A shell command copying stale files from a sibling `out/` directory does not. Use the same pattern for generated OpenAPI JSON, configuration summaries without secrets, or immutable batch assets.

When resource names depend on contents for cache busting, hash the tracked input bytes, generate a mapping, and make both renamed files and the mapping outputs of the same task. Preserve relative path structure and detect collisions rather than flattening filenames. Serve the generated mapping from the packaged classpath so runtime behavior matches the build artifact.

A generator implemented by the application itself must not depend on the application's final `compile` while also feeding `generatedSources`. Extract a `generator` module upstream and invoke its compiled tool using a subprocess or isolated classloader; its input schema and tool classpath become dependencies of the consuming task. For a simple reusable build-time library, header imports can suffice; use isolated workers/subprocesses when classpath conflicts or differing tool versions require separation.

Share conventions as a small trait with configurable source paths/options. Do not force all modules to execute a generator when they do not use it. If dozens of repositories need the same integration, package the trait as a tested Mill plugin and check binary platform compatibility. In a single repository, a helper file or meta-build source may be easier than publishing a plugin.

Validation should establish output correctness, stale-output cleanup, repeatability, and rebuild boundaries. Include a malformed-input failure if the generator has relevant validation behavior. Confirm downstream tests run against the generated code/resources, not against a manually checked-in copy. Persistent task destinations need extra stale-file management because old generated classes can survive source removal.
