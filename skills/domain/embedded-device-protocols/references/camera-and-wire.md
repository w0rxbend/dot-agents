# Camera frames and device wire compatibility

Paired public implementations: [spycam FrameProtocol.h](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/include/FrameProtocol.h), [spycam-s3 FrameProtocol.h](https://github.com/worxbend/spycam-s3/blob/71e0ef4b7c55a2313f596710e53d3f52ddec19cc/lib/frame_protocol/src/FrameProtocol.h), [instachron device parser](https://github.com/worxbend/instachron/blob/20cbe22e947d5bfec2a86783886935b0bef196d3/services/tcp-camera-backend/internal/protocol/protocol.go). Numeric widths/order are part of deployed ABI:

| Variant | Prefix before JPEG bytes | Fields |
|---|---|---|
| JPGS legacy | 16 bytes | four-byte magic, uint32 sequence, uint32 JPEG payload length, uint32 device millis |
| JPGD device | 20 bytes | same 16 bytes with JPGD magic, then uint32 camera ID |

Fields are big-endian. Payload length counts JPEG bytes only, not camera-ID extension. Reading JPGD packet as 16-byte legacy header leaves camera-ID bytes in stream, corrupting framing. Decode magic before choosing remaining prefix length. Device millis is wraparound uptime counter, not wall-clock Unix time. Both firmware peers emit same JPGD prefix. Protocol edits need byte fixtures from both peers and host parser, without copying their different board/camera settings.

[proxy-to-proxy streamproto](https://github.com/worxbend/instachron/blob/20cbe22e947d5bfec2a86783886935b0bef196d3/shared/streamproto/streamproto.go) is separate 32-byte MJPG protocol: version/header fields, nanosecond timestamp, camera ID, uint64 sequence, payload length. Do not merge it with firmware ingress just because both carry JPEG. Validate exact-read behavior, maximum/zero length, EOF in each prefix segment, truncated JPEG, plausible SOI/EOI markers and multiple frames in one transport read. JPEG marker checks do not prove full image validity. Keep allocation caps before allocating advertised length.

TCP reads/writes are not packet boundaries. Sender must handle partial writes and bound elapsed send time. After partial failed frame, close connection so next header is not read as old payload. [spycam sender](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/src/TcpFrameSender.cpp) reconnects before holding camera buffer and disconnects after send failure. [spycam-s3 sender](https://github.com/worxbend/spycam-s3/blob/71e0ef4b7c55a2313f596710e53d3f52ddec19cc/src/TcpFrameSender.cpp) keeps same connection-before-borrow and close-after-partial-failure boundary. Both sender tasks release borrowed frame regardless of success. Follow that ownership through latest-frame slot too: replacing stale frame must return old driver buffer exactly once. Do not keep borrowed framebuffer across reconnect sleep or use it after return.

Camera configuration in [CameraManager.cpp](https://github.com/worxbend/spycam/blob/518a969f8dbff638fb1a7c299958ee7c62655d61/src/CameraManager.cpp) selects PSRAM/DRAM and frame-count fallbacks. Before increasing resolution or buffer count, check target board and [Espressif camera driver](https://github.com/espressif/esp32-camera). More buffering can increase latency or exhaust memory.

LED control uses other ABIs. [led-matrix-controller parser](https://github.com/worxbend/led-matrix-controller/blob/6061b81763740885d61af745e14cc633aa35c2e6/src/FrameParser.cpp): five-byte header, uint8 payload length, XOR checksum. Its buffer must fit header + 255 + checksum. [neoncore MatrixProtocol](https://github.com/worxbend/neoncore/blob/6eb16847d95ff6cd0847c32c1a3b698f3057ce98/src/MatrixProtocol.cpp) has own status command/response. Preserve explicit resynchronization/error behavior and shared byte vectors. Do not carry opcodes across projects by name. Test garbage prefix, partial header/body, checksum error, maximum length and recovery into next valid frame.
